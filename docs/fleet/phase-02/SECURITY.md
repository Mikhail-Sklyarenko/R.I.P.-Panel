# Phase 02 security

Secrets remain on the PC that owns the vault. The catalog snapshot and `catalog_cache` have no login, password, shared secret, or maFile body. Binding history stores SteamID64 and a source string only. Agent tokens are stored as SHA-256. Logs written by these paths do not include the fleet token or the agent token.

When the coordinator has an assignment book, which `FleetHost` always attaches, a heartbeat must be `registered` and must present that agent's own token. `unregistered` and `revoked` are rejected. A revoked agent is not accepted with the shared fleet token. The shared token identifies the fleet on `POST /v1/heartbeat`. It does not authorize `GET /v1/status` or `POST /v1/operator`.

Those operator routes accept only a distinct operator token, in `X-Operator-Token` or `Authorization: Bearer`. `X-Fleet-Token` is not read on those routes. An agent token is not an operator token. The operator token must differ from the fleet token and is generated when the caller does not supply one. `FleetHost` stores it with the same DPAPI helper as agent tokens, at `data/fleet/credentials/operator.bin`. It is not written into `wingman_fleet.json`, the `start_coordinator` return value, or the log line.

Enrollment is a one-time code stored as a SHA-256 hash with a five-minute expiry. `POST /v1/enroll` returns the new agent token and `registration_generation` once. The panel shows the code in the status text and does not write it to the log line. The agent PC stores the token with Windows DPAPI under `data/fleet/credentials/`. The Steam vault is not used for this token. The token is not written into ordinary logs.

`SIMULATION` does not open a socket. `LOCALHOST_DEVELOPMENT` binds `127.0.0.1` without TLS and logs that this is not a LAN deployment. `SECURE_LAN` requires a certificate, a private key, and a CA file, then binds with TLS 1.2 or newer. Cleartext HTTP on any other address is refused. `HttpTransport` builds the SSL context with `ssl.create_default_context` and rejects HTTPS that has no CA file. Certificate verification is not a switch that can be turned off.

`lan_ready` is true only when the mode is `secure_lan`, the listener is TLS, the certificate and CA files exist, and all four roster agents are `registered`. `four_pc_proven` is always false. A passing localhost HTTPS test is not a LAN trial. Bootstrap stays a one-time enrollment code. HTTPS still requires the configured CA; the operator split does not turn certificate checks off.

A manual SteamID64 and `loginusers.vdf` do not produce `verified`. Verification is one IdentityProbe measurement: local Steam, plus one fresh GSI snapshot when GSI is present. Two current sources that disagree are `MISMATCH` even when one of them equals the expected SteamID64. That status is kept through the agent, the local catalog, and the assignment book. A matching id with `unconfirmed`, `manual`, or `loginusers` is not VERIFIED. A stale GSI is not a source. A fresh GSI with no local Steam id can be a proof. Applying `WindowsBackend.apply_identity_assignment` only changes the expected id. It does not set a verified flag. There is no flag that disables process fencing.

`ResultStatus.COMPLETED` is required before evidence can verify a slot. `FAILED`, `UNCONFIRMED`, `EXPIRED`, `REJECTED`, and `ACCEPTED` do not. An acknowledgement means the terminal result was stored. It does not mean the SteamID64 was confirmed. A new registration does not inherit the previous catalog's trust or a previous READY. A catalog head with `registration_generation=0` after a v4 migration is not assignable. RunPlan is built only from the current fresh proofs. SECURE_LAN still verifies certificates; there is no `verify=False` path.

Assignment commands do not call the game backend and do not grant a gameplay lease.
